## Evidence and provenance

Public availability, exact revisions, weight-file byte sizes, license-file hashes and model-card hashes are recorded in [model-research.json](../benchmarks/results/system-one-judges-2026-11-11/model-research.json), with additional official Mini/Flash/Decider releases in [candidate-artifacts.json](../benchmarks/results/system-one-judges-2026-11-11-quality-extension/candidate-artifacts.json). The Hugging Face API and revision-pinned files were fetched without credentials. Availability of metadata alone is not proof that every runtime works; seven actual GGUF files, including Granite, Edge and Mini Q8/Q4 artifacts, were hashed. An artifact rejected by memory admission is not counted as an executed model.

The 60 frozen fixtures were labeled from content and an explicit rubric before inference. Granite decisions were never used as labels. Twelve are historical database texts; the remainder are constructed cases. Labels are provisional, assigned by the evaluation author, and have not received independent human adjudication. Historical T2 storage proves prior retention, not factual truth or usefulness. The sampled Postgres-vs-SQLite claim, for example, is evaluated for durability of content, not accepted as a verified description of Penumbra. This pilot cannot establish factual memory quality or downstream benefit.

## Current implementation and fleet audit

The daemon's dreaming pool resolves the `dreaming-judge` role from agentchat configuration. The inspected roster names Granite 4.1 3B Q8, Gemma E4B and Qwen3.5 4B seats through the loopback proxy. The proxy's read-only `/v1/models` response advertised Kapitsa and Qwen3.8 Flash-Next, not these judge identifiers. A separate existing server at port 8086 did have Granite loaded. The benchmark uses that resident Granite server directly; it is a **single-seat baseline**, not a measurement of the complete P1 quorum or proxy routing. No model-loading probes were sent to fleet workers.

The existing launch configuration sets `PENUMBRA_TYPESAFE_JUDGE_PROMOTION=veto`. This work neither activated nor disabled that pre-existing setting. Stored `judge_decisions` contained 8,493 promotion and 822 efficacy shadow rows for `jev-1.13.0` at inspection. Five sampled T1 identifiers had stored Jev rows; three had matching bodies by SHA-256; they are an optional historical reference, with no new hosted inference.

The installed Granite runtime was llama.cpp `97f06e9e...`; it predates the current native System One implementation. An independent experimental build at `2cbe0ec429b849a88664e0f62388fc92a5abd699` was compiled with Metal, two build jobs, and no UI asset downloads. No installed binary, launch configuration, fleet routing or worker model was changed. The temporary decision server bound loopback port 18944.

The continuation installs that same native source revision separately as a versioned HTTP-only runtime, with OpenSSL disabled and relocatable local libraries. Static inspection of its executable and all17 unique installed dylib/executable files found no unexpected absolute runtime dependency. This avoids a new Homebrew OpenSSL4 dependency without replacing Granite's runtime or upgrading a fleet agent. ModelRun's per-workload binary setting can express the dedicated runtime; deployed proxy parity and managed restart behavior still require direct validation.

## Licensing consequences

Apache-2.0 candidates require preserving their license, applicable NOTICE/attribution and modification notices when redistributing; check each artifact's included upstream components. Their availability does not make an unlabeled downstream conversion trustworthy. Downloaded model files remain outside git.

The exact d1 license defines its threshold at $10M annual revenue and conditions commercial rights on the threshold provisions. It also requires license/notice preservation and notices for modified files. Do not present it as Apache-2.0 or unrestricted OSS. GLiDE's license requires a separate agreement above $10M revenue for commercial production use, commercial “Built with Fastino GLiDE” attribution, carry-forward restrictions for derivatives, and preservation of upstream notices. Its evaluation allowance is distinct from production permission. Drex's modified terms include >$1M revenue or funding restrictions with stated personal/research exceptions, competitor restrictions, use restrictions and enforceable downstream terms. None should become Penumbra's unconditional bundled default.

## Public evidence, kept separate

- **Vendor measurements:** d3 Nano's card reports Decision Index 0.3.2 overall 38.9 and 13.4 ms median on MI325X. Liquid reports d1-3B's 48.57 on **0.2.1 public split**, and 30 ms on **M5 Pro**. These are different suite versions/splits/hardware and are not a ranking or M4 estimate. GLiDE 0.4B/9B reports 6.9/38.6 ms on RTX PRO 6000. None is a Penumbra measurement.
- **Independent third-party experiment:** [system-one-bench](https://github.com/alilibx/system-one-bench) publishes frozen requests, accuracy/calibration results and local CPU runs for d1/d3. Its local CPU latency is explicitly separate from hosted latency. This supports testing these models, not importing its calibration to Penumbra. The published suite is not a memory-promotion benchmark and was not reproduced here.
- **Independent research:** [Dinzinger et al., 2026](https://arxiv.org/abs/2610.32318) found decision fine-tuning did not beat dedicated reranker fine-tuning on their retrieval tasks, and calibration depended on question wording. This is evidence against universal superiority, not a claim about memory promotion.
- **Local experiments:** only the version-pinned runs and telemetry in [the benchmark report](../benchmarks/system-one-judges.md) count as local quality/resource evidence. No vendor number fills a missing cell.

## Hardware and integration constraints

[llama.cpp's native API](https://github.com/ggml-org/llama.cpp/blob/2cbe0ec429b849a88664e0f62388fc92a5abd699/tools/server/README.md#typesafe-compatible-api-endpoints) supports typed decisions for particular decision architectures, not arbitrary chat weights. Its [readout implementation](https://github.com/ggml-org/llama.cpp/blob/2cbe0ec429b849a88664e0f62388fc92a5abd699/tools/server/server-decision.cpp) applies model-specific temperatures and confidence definitions. Never equate provider confidence with maximum option probability across models. Model-specific heads, templates, bidirectional attention and whole-prompt microbatching must survive conversion.

Metal is tested locally for the executed GGUFs. CPU/Metal availability in llama.cpp does not establish acceptable latency for every supported model. AMD MI325X evidence does not establish AMD Strix Halo performance: GPU architecture, ROCm support, memory topology and the Gufo serving path differ. No experiment displaced Kapitsa or Gufo. The Z13 had 21,960,675,328 available bytes, only about 0.45 GiB above the repository's 20 GiB admission floor. A MacBook capacity SSH probe failed authentication; no inference or configuration probe followed.

The experimental local client accepts an explicit server origin, model and revision, rejects unsolicited remote endpoints and redirects, bounds request bytes/concurrency/deadlines/retries, validates the existing wire schema plus probability normalization/choice/legend consistency, and returns failures as abstentions. Its diagnostics contain hashes, identifiers and timings, not memory bodies or secrets. The model revision is an operator-supplied artifact pin, not cryptographic attestation by the server; verify downloaded hashes before launch. Native prompt escaping plus untrusted-state instructions reduce injection exposure; neither is a proof of immunity.

The [November 12 Strix Halo NPU investigation](system-one-z13-npu-feasibility.md) adds a distinct execution route: FastFlowLM1.0.12 has native System One serving for d3 Lite/Nano on XDNA2.
