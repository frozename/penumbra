## 1) Current dispatch pipeline (as implemented today)

### 1.1 Entry and chain-start handling

1. HTTP entrypoint receives `POST /chains/start` and routes to `chainsStartRoute(...)` in `packages/daemon/src/serve.ts:649-650`.
2. `chainsStartRoute(...)` parses JSON and calls `chainStartFromInput(...)` in `packages/daemon/src/routes/chains.ts:83-87`.
3. `chainStartFromInput(...)` validates against `ChainStartRequestSchema` (`packages/daemon/src/routes/chains.ts:51`; schema at `packages/core/src/schemas/chain.ts:5-20`) and forwards to `chainStartInternal(...)` (`packages/daemon/src/routes/chains.ts:78-80`).
4. `chainStartInternal(...)` normalizes routing and creates the chain-start handoff row (`packages/daemon/src/routes/chains.ts:89-329`).

### 1.2 Handoff row creation and queueing semantics

1. `chainStartInternal(...)` creates IDs/timestamp and writes a t0 user-prompt event (`packages/daemon/src/routes/chains.ts:269-294`).
2. It then inserts an already-approved handoff via `services.handoffWriter.createApproved(...)` (`packages/daemon/src/routes/chains.ts:296-313`).
3. `createApproved(...)` persists `status='approved'` into `handoffs` in `packages/core/src/writers/handoff.ts:73-94`.
4. The `handoffs` table schema currently has no `dispatch_kind` field (`packages/core/src/db/schema.ts:94-118`) and no additive migration for such a field (`packages/core/src/db/schema.ts:508-524`).

### 1.3 Worker discovery and claiming

1. Worker subscribes + polls pending rows via `startEventSource(...)` (`packages/agentchat/bin/agentchat-worker.ts:1089-1101`; event loop at `packages/agentchat/src/worker/event-source.ts:31-91`).
2. Worker only listens for `approved` and `redirected` statuses (`packages/agentchat/bin/agentchat-worker.ts:1094`).
3. Dispatcher claims each row before execution (`packages/agentchat/src/worker/dispatcher.ts:100-103`) via daemon `/handoffs/:id/claim` (`packages/agentchat/bin/agentchat-worker.ts:902`).
4. Claim route flips row to `dispatched` through `handoffWriter.claimDispatch(...)` (`packages/daemon/src/routes/handoffs.ts:194-245`; SQL transition at `packages/core/src/writers/handoff.ts:150-156`).

### 1.4 Worker dispatch path to ACP session

1. Worker dispatch lambda builds runtime context (cwd override, transcript, trust settings, executor) in `packages/agentchat/bin/agentchat-worker.ts:917-1036`.
2. It calls `dispatchHandoff(...)` in `packages/agentchat/bin/agentchat-worker.ts:1037-1061`.
3. `dispatchHandoff(...)` selects prompt once per hop at session start:
   - chain-start hop (`from_agent==='user'`): `promptText` is `undefined`, so raw handoff `message` is used as the turn input (`packages/agentchat/src/cli/dispatch-handoff.ts:70-76`).
   - non-chain-start hop: `buildNextPrompt(...)` is used (`packages/agentchat/src/cli/dispatch-handoff.ts:73-76`).
4. `runChatTurn(...)` resolves final prompt as `input.prompt ?? input.userMessage` and sends exactly one dispatch input prompt (`packages/agentchat/src/cli/loop.ts:43`, `packages/agentchat/src/cli/loop.ts:79-90`).

### 1.5 ACP session spawn and prompt send

1. Adapter creation is YAML-option-driven:
   - config YAML parse: `packages/agentchat/src/config/load.ts:6-17`.
   - adapter options forwarded from config to adapter constructors: `packages/agentchat/src/adapters/registry.ts:13-33`, `:73-99`.
2. `stdio-acp` flow:
   - starts child ACP server: `packages/agentchat/src/adapters/stdio-acp.ts:114-120`.
   - builds `session/new` params with `mcpServers`: `packages/agentchat/src/adapters/stdio-acp.ts:379-409`.
   - opens session: `packages/agentchat/src/adapters/stdio-acp.ts:413-414`.
   - sends one `session/prompt` with the final prompt: `packages/agentchat/src/adapters/stdio-acp.ts:563-566`.
3. `opencode-acp` flow:
   - translates mcp servers into a per-dispatch temp XDG config directory: `packages/agentchat/src/adapters/opencode-acp.ts:116-120`, via `packages/agentchat/src/adapters/opencode-mcp-config.ts:43-75`.
   - opens session: `packages/agentchat/src/adapters/opencode-acp.ts:141-143`.
   - sends one `sendMessage(...)` for the turn prompt: `packages/agentchat/src/adapters/opencode-acp.ts:157-162`.

### 1.6 Terminal transition

1. Dispatcher posts `complete` at end (`packages/agentchat/src/worker/dispatcher.ts:331-338`; wired in worker at `packages/agentchat/bin/agentchat-worker.ts:904`).
2. Daemon `/handoffs/:id/complete` transitions `dispatched -> completed` (`packages/daemon/src/routes/handoffs.ts:247-250`).
3. Failure path is `/handoffs/:id/fail` (`packages/daemon/src/routes/handoffs.ts:342-360`).
4. This is the cleanest lifecycle seam for invoking `handleTickTeardown(...)` (`packages/daemon/src/long-lived/teardown.ts:18-101`) after long-lived dispatches finish.

## 2) Answers to Phase 9.3 blocking questions

### 2.1 Q1: `dispatch_kind` plumbing

Question: should `dispatch_kind=long_lived_tick` live only in chain_start payload, or be stored on handoff rows?

Recommendation: **both** payload + persisted row.

Rationale:

1. Payload-only is insufficient after enqueue. Worker/terminal routes operate on handoff rows, not original request body (`packages/agentchat/bin/agentchat-worker.ts:1089-1101`, `packages/daemon/src/routes/handoffs.ts:247-265`, `:342-367`).
2. Teardown needs durable classification when completion happens, potentially much later than spawn (`packages/daemon/src/long-lived/teardown.ts:18-101`).
3. Long-lived tick identity is already persisted in `long_lived_ticks` (`packages/core/src/db/schema.ts:624-637`), so persisting dispatch linkage on the handoff row keeps correlation local at terminal routes.

Proposed field placement:

1. Chain-start input schema: add `dispatch_kind`, `long_lived_agent_id`, `long_lived_tick_id` to `packages/core/src/schemas/chain.ts:5-20`.
2. Handoff DB schema migration: add `dispatch_kind`, `long_lived_agent_id`, `long_lived_tick_id` to `handoffs` table and additive migration block in `packages/core/src/db/schema.ts:94-118` and `:508-524`.
3. Handoff row schema type: add same fields in `packages/core/src/schemas/handoff.ts:17-48`.
4. Writer plumbing: extend `CreateApprovedParams` and SQL insert in `packages/core/src/writers/handoff.ts:12-31` and `:77-93`.
5. Chain-start insertion call-site: thread values through `services.handoffWriter.createApproved(...)` in `packages/daemon/src/routes/chains.ts:296-313`.

Decision: **store on handoff row** (authoritative), while still threading in chain-start payload for spawn-time behavior.

### 2.2 Q2: prompt composition insertion point

Question: where is prompt composed today (once-at-session-start vs per-message), and where should `stampPrompt(...)` be called?

Observed behavior:

1. Prompt for a handoff hop is computed once in `dispatchHandoff(...)` (`packages/agentchat/src/cli/dispatch-handoff.ts:70-89`).
2. `runChatTurn(...)` then sends one dispatch prompt (`packages/agentchat/src/cli/loop.ts:43`, `:79-90`).
3. ACP adapters each submit one turn prompt (`packages/agentchat/src/adapters/stdio-acp.ts:563-566`; `packages/agentchat/src/adapters/opencode-acp.ts:157-162`).

Therefore, long-lived prompt stamping should happen once before worker execution.

Recommended insertion point:

1. Call `stampPrompt(...)` from daemon chain-start path immediately before writing the approved handoff row.
2. Concrete seam: `packages/daemon/src/routes/chains.ts` around the transaction block (`:276-319`), replacing `message: input.message` at `packages/daemon/src/routes/chains.ts:303` with a precomputed `stampedMessage` for `dispatch_kind='long_lived_tick'`.
3. Stamping helper to call: `packages/daemon/src/long-lived/prompt-stamper.ts:19-63`.

Why this seam:

1. Long-lived state (`standing_brief`, `working_memory`, `mcp_allowlist`) is in daemon-owned tables (`packages/core/src/db/schema.ts:598-614`), not in agentchat worker memory.
2. Keeping worker untouched avoids cross-package coupling and preserves existing turn semantics.

Decision: **stamp in daemon chain-start before `createApproved(...)`**.

### 2.3 Q3: tool-registry stamping mechanism

Question: choose among:
- (a) per-session MCP server instance with filtered registry,
- (b) shared MCP server with per-session filter via session header,
- (c) adapter-layer interceptor dropping non-allowlisted calls.

Recommendation: **(a) per-session registry filtering, with server-side enforcement wrapper**.

Why (a) fits this codebase:

1. ACP sessions are already configured per dispatch/session via `mcpServers`:
   - stdio path: `packages/agentchat/src/adapters/stdio-acp.ts:379-409`.
   - opencode path: `packages/agentchat/src/adapters/opencode-acp.ts:116-120` + `packages/agentchat/src/adapters/opencode-mcp-config.ts:43-75`.
2. Current mechanism already injects per-dispatch env into penumbra MCP entry (`PENUMBRA_HANDOFF_ID`) at `packages/agentchat/src/adapters/stdio-acp.ts:392-404`; same seam can inject `running_agent_id`, `tick_id`, and allowlist payload.
3. MCP registry is centrally registered in one place (`packages/mcp/src/server.ts:7-12`), which is the right interception point for filtering exposed tools per process/session.

Why not (b):

1. Current penumbra MCP transport is stdio (`packages/mcp/bin/penumbra-mcp.ts:2`, `:42`), not HTTP with session headers.
2. No existing session-header plumbing exists between ACP tool calls and MCP tool handlers.

Why not (c):

1. Adapter permission path only yields binary `approve|reject` (`packages/agentchat/src/sdk/adapter.ts:11`; callback impl `packages/agentchat/src/worker/permission-callback.ts:38-61`).
2. Long-lived action-gate requires richer outcomes (`executed`, `queued`, `snapshot/cooldown`, structured rejection) as defined in `packages/daemon/src/long-lived/action-gate.ts:56-67` and `:77-194`; adapter interceptors cannot express this without protocol extension.

Concrete interception/filtering location:

1. Filter surface (tool exposure): `packages/mcp/src/server.ts:7-12` (before `server.registerTool(...)`).
2. Session-scoped context injection feeding that filter: `packages/agentchat/src/adapters/stdio-acp.ts:392-409` and opencode equivalent at `packages/agentchat/src/adapters/opencode-acp.ts:116-120`.

Decision: **(a)**.

5. Adapter-level gating mismatch: permission callback surface is approve/reject only (`packages/agentchat/src/sdk/adapter.ts:11`, `packages/agentchat/src/worker/permission-callback.ts:38-61`), while long-lived gate requires queued + snapshot/cooldown behavior (`packages/daemon/src/long-lived/action-gate.ts:56-67`, `:108-169`).
